## 1. 最重要: 設計の分離 (ここを混ぜると必ず破綻する)

今日いちばん時間を溶かした原因は、**お手本の見た目と判定を同じデータで兼ねていた**こと。
字形を直しても直しても別の所が崩れ、塾長を何度も往復させてしまった。現在は完全に分離済み。

| 層 | 実体 | 役割 | 触るときの注意 |
|---|---|---|---|
| **お手本の字** | フォント (Klee One サブセット `public/fonts/KleeOne-subset.woff2` 23KB) | 画面に見える字。`renderGuide.renderBackground` が `fillText` で描く | **線データで描き直さないこと**。字形が崩れる元凶 |
| **書き順の案内** | 番号 + 書き出しの点 + 向き矢印のみ | どの画から書くかを示す | **画の経路を線でなぞって見せない** (§下記) |
| **判定** | 線データ `src/data/characters/*.json` (非表示) | **書き出しの位置と画の順番だけ** (§下記 2026-08-18) | 見た目の責任は無い。書き出しの当たり判定と割り切る |

### ★ 判定は「書き出しの位置と順番」だけ (2026-08-18 塾長指示)
なぞり判定 (経路逸脱・逆走・到達率) は**廃止**。経路は画面に見せていないのに
「せんのうえをなぞってね」「ぎゃくむきだよ」と途中で叱られるのは、子どもには
意味の分からないエラーになる (実際の練習で塾長が確認)。いまの判定は:
- 書き出し: 現在の画の始点に触れたら開始。終点側からなら「こっちから」、
  別の画の始点なら「つぎは◯かくめ」、どれでもなければ点を点滅
- 途中: **何も言わない**。どう書いても自由
- 離したとき: 描いた長さが画の 35% (上限0.45・点は0.04) あれば完了。
  タップだけなら「さいごまで かこうね」
実装は `MatchParams.pathJudge` (アプリは false / 単体テスト・データ検査は true のまま)。
★エンジンのなぞり判定コードは**消さない**: 教材データの健全性検査
(理想軌跡が通ること) の物差しとして使い続けている。
- ★開始のみ判定では書き出しの受付半径 `startTol` を **0.13 で頭打ち**にする
  (2026-08-18)。経路判定があった頃は長い画で 0.28 (マス1/3) まで膨らんでも
  経路で正されたが、書き出しが判定の全てになると別の場所から書いても通る。

### ★ 書いている途中は声を出さない (2026-08-18 塾長指示)
1画ごとの「つぎは にかくめ」も、書き出しを外したときの「ここから かいてね」も
**廃止**。子どもの手より発話が遅れて、ずっと喋り続けることになる。
残すのは「字を開いたときの読み上げ」と「完走したときの称賛」だけ
(`PracticeScreen` の `playStrokeSuccess` / `playFeedback` / `playTogether` /
`playRetryVoice` の呼び出しを外した。効果音 pop/complete は残す)。
案内は**番号バッジの拡大と書き出しの点の点滅**だけで行う。

### ★ 経路を線で見せてはいけない (PR #39)
お手本 (フォント) と線データの経路は一致しない。経路を描くと「お手本と違う線」を
子どもに見せることになり、「なぞり方がおかしい」となる。塾長の判断で**経路表示は廃止**。
書き順は塾長提供のなぞり書きプリントと同じ「番号 + 書き出し」方式で示す。
`renderGuide.ts` の `dottedStroke` と `playDemo` は削除・停止済み。**復活させないこと。**

### ★ お手本は消さない (PR #37)
「何度でも練習できるように」との方針。レベルに関わらず常に同じ濃さ (`GUIDE_SOLID`) で表示する。
薄くするのも「消えた」のと同じ。
なお**消していた真犯人は描画側だった** — §5 の canvas.width の項を必ず読むこと。

### ★ 例外は運筆 (せんのれんしゅう) だけ (2026-08-17)
運筆は「字」ではないので手本フォントに字形が無い。文字コード (〽 ◎ 🪜 ⛰) を借りて
いるだけなので、フォントで描くと**絵文字のはしごや山**が出る。しかも判定する線とは
別物だった。運筆に限りお手本を線データから描く。この場合お手本と判定が同一データに
なるので、上の「経路を見せない」で避けたかった問題 (お手本と違う線を見せる) は起きない。
`PracticeScreen` が `type === 'unpitsu'` のとき `char` を渡さないことで切り替える。

## 5. 落とし穴 (実際に踏んだもの)

- ★★ **canvas.width への代入は「同じ値でも」中身を消す** (HTML 仕様)。
  `CanvasSurface.layout()` は ResizeObserver のたびに再代入していたが、描き直しは
  「寸法が変わったときだけ」だったので、**2字目からお手本もマス目も真っ白**になっていた。
  2026-08-17 に修正 (寸法が同じなら canvas に触らない)。塾長が繰り返し言っていた
  「お手本が消える」の正体はこれ。#36 #37 はデータ側を常時表示にする対策で、
  消していた張本人には届いていなかった。回帰テストは E2E で**背景層の画素を数える**
  (DOM を見ても分からない。1字目は正常なので「戻って2字目」まで見ること)。
- ★ **見た目の事故は自動テストをすり抜ける**。判定の許容幅が広いので、お手本が
  真っ白でも絵文字でも 830件は緑のまま通った。**必ず画面を撮って自分の目で見る**
  (`tools/qa-sheet.mjs`)。
- ★ **字形を測るツールは、アプリと同じ条件で描くこと**。refit-glyphs は 0.88em・
  中央に描いてお手本としていたが、アプリは 0.86em・y=0.52。別の字に合わせ込んで
  いたので、忠実度 76% という数字自体が誤りだった (実際は 49.3%)。
- ★ **手本フォントを system の名前 ("Klee One") で引かない**。コンテナを作り直すと
  フォントが消え、**黙って代替フォント (IPAGothic 等) を測る**。その状態で
  `refit-glyphs --apply` を回すと全文字が静かに壊れる。`tools/ref-font.mjs` が
  出荷している woff2 を読み、効いていなければ例外で止める。字形を扱う新しい
  ツールは必ずこれを使うこと。
- ★ **別の画の書き出しに吸着した頭は、開始のみ判定で「誤った画の受理」になる** (2026-08-18)。
  合わせ込みの事故で ち の1画目 (横棒) の書き出しが縦画の頭 = 2画目の書き出しと
  同じ点に置かれ、縦を先に書いても1画目として通り、次に同じ場所で「2画目」を
  書かされた (塾長が実練習で発見)。同型が 10字 (ち・ふ・ま・よ・ら・ょ・ケ・チ・ッ・ゥ)。
  始点は墨の上にあるので `check-start-dots` の浮き検査は通ってしまう。
  いまは同検査が**書き出しどうしの距離 (0.045 未満 = 同じ点) も落とす**
  (ロ・ク・タ・5 のように本当に同じ角から書く字は許可リスト)。
  直すときの手順: `tools/_rows.mts` で墨の行プロファイルから中心線を実測 →
  手で置く → `refit-glyphs` で忠実度を測る (経路探索の候補は交差部で蛇行することが
  あるので、採用したら必ず overlay-sheet を目で見る。ま で実際に蛇行した)。
  小書き字 (ょ・ッ・ゥ) は基字を直してから相似変換で丸ごと運ぶ:
  ょ←よ [0.768,0.768,+0.117,+0.221] / ッ←ツ [0.766,0.768,+0.123,+0.229] /
  ゥ←ウ [0.771,0.766,+0.116,+0.211]。
- ★★ **「書き出しが墨の上にある」だけでは足りない — 画の切り分けそのものが違う字がある**
  (2026-08-18 塾長が実練習で や・を・わ を発見)。合わせ込みの campaign で線が
  隣の墨に乗り移り、**別の画の途中から書かせる**データが 18字に残っていた:
    や … 右上の点を書く画が無く、長い払いが2本に割れていた
    わ … 2画目が1画目 (縦) の途中から始まり、横棒の左半分は誰も書かない
    を … 3画目が本来の書き出し (右上) ではなく、終点側の左下に置かれていた
    き … 2本の横棒に線が乗っておらず、斜めに横断していた
  **見つけ方**: `tools/render/coverage-sheet.mts` が「どの画も通っていない墨」を赤で描く。
  赤が**書き出しの手前**に続いていたら案内が壊れている (輪の内側の赤は無害)。
  **機械で止める**: `tools/check-stroke-segmentation.mts` (gates に登録済み) が
  ① 書き出しの手前に「誰も書かない墨」がその画の向きのまま続いていないか
  ② どの画も通らない部品が無いか
  の2つだけを見る。★他の画の墨が手前にあるのは正常 (ま の縦画が横棒から始まる等) なので、
  「他の画が書く墨」を除いてから判定すること。ここを除かないと 18字が誤検出で埋まる。
  **直し方**: `tools/_tips.mts` で墨の端点を出す → `tools/retrace_spec.json` に
  各画の通過点 (書き出し・要所・終わり) を書く → `tools/retrace.mts --apply` が
  墨の中を経路探索して引き直す。制御点を手で並べるより速く、墨から浮かない。
  ★切り分けに迷ったら **Phase 7 の手書き原データ** (`git show 3328287:...json`) を見る。
  座標は粗いが「どの画がどの部品か」の意図はそこにある。
- ★ **端点を「墨に入るまで」歩かせるときは、歩ける距離を実際のズレに比例させる**。
  一律の上限 (0.26) にしていたら、ほぼ乗っている端点が墨の帯の少し上を
  かすめたまま 0.30 歩き、反対の端に端点を置いて「行って戻る」ジグザグを作った
  (こ・ミ・モ・ユ で発生)。忠実度 100%・始点も墨の上・長さ下限も通過で、
  **どの検査もすり抜けた。捕まえたのは目視だけ**。いまは弧長の伸縮ガードで機械でも止まる。
- ★ **データの画とフォントの画は「切り分け」からして違うことがある**。と の1画目は
  データでは上の縦棒だったが、フォント (教科書体の筆順) では「右上のふくらみから
  始まる2画目」の解釈で、1画目は上の斜め棒。き・も は横画が1段ずれていた。
  空き墨 (他の画の帯を除いた墨) の連結成分を測ると正しい置き場所が分かる。
- ★ **向きを隣り合う2点で測らない**。線データは墨に合わせ込んであるので細かい凹凸が
  あり、2点で測ると「右へ進む画なのに上向き」と出る。矢印は**書き出しの点から
  弧長2割ぶん先へ向かう向き**で描く (`startDirection`)。画の途中の接線で描くと、
  折れ角でお手本と無関係な向きを指す (2026-08-17 塾長指摘「書き順の誘導がおかしい」)。
- ★ **番号は画の脇に置く**。ずらし幅を大きくすると (旧 0.07+0.03)、どの画の番号か
  分からなくなる。書き出しの点に触れる程度 (0.055+0.022) に留める。
- ★ **運筆 (せんのれんしゅう) に手本フォントは無い**。文字コード (〽 ◎ 🪜 ⛰) を
  借りているだけなので、フォントで描くと絵文字が出る。運筆はお手本を線データから
  描く (お手本と判定が同一データなので PR #39 の問題は起きない)。
- **「直っていない」の切り分け**: ホーム右下のビルド刻印を見る。刻印が古ければ配信の問題、
  新しければデータの問題。これを入れるまで何往復もした。
- **キャッシュ**: `/kakijun/` は拡張子が無いので `vercel.json` の `/(.*\.html)` ルールに当たらない。
  個別に no-cache を指定済み (#32)。
  ★2026-08-18 から**開きっぱなしのタブも自動で新ビルドに切り替わる** (main.tsx が
  1分ごと + タブ復帰時に SW の更新を確認し、切り替わったら一度だけ再読み込み)。
  それまでは「開いたままのタブは新ビルドを取りに行かない」= 塾長の画面だけ古い、
  が頻発していた (き の書き順ズレ報告の正体もこれ。判定データは直っていたのに
  画面の中身が3日前のビルドだった)。★この仕組み自体が古いビルドには無いので、
  **自動更新が入る前のタブは手でリロード2回**が最後に一度だけ要る。
- **`vercel.json` に未知のキーを足さない** (`comment` 等)。スキーマ検証で落ちてデプロイが止まる。
- **長さ0の画は判定エンジンを固める**。`step()` に下限を入れ、退化画を弾く検査も追加済み。
- **コンテナから本番 URL へは出られない** (プロキシ制限)。配信確認は塾長の画面かビルド刻印で。
- **`.claude/` は gitignore** される。ルールや手順はリポジトリ内 (この文書等) に書く。

## 6. 検査・調査ツール

## 7. 次のセッションへの申し送り

塾長は**修正の往復が多いことに強い不満**を持っている。以下を守ること。

1. **出す前に自分の目で実画面を見る**。Playwright でスクリーンショットを撮ってから報告する。
   検査が緑でも見た目が壊れていることがある (今日それで何度も差し戻された)。
2. **数値だけを根拠にしない**。忠実度95%でも見た目が変だった例がある。
3. **直せないときは正直に言い、代替案を出す**。塾長は「できないなら載せないで」と言ってくれる。
4. 塾長の提案 (例: 「見本の画像の上から書かせればいい」) は**正しいことが多い**。まず検討する。
5. **「検査が緑」を報告に使わない**。2026-08-17 の事故は 829件緑のまま本番で
   真っ白だった。報告するのは「何を自分の目で見たか」。
6. 判定のデータをいじったら、**必ず `npm run gates` と目視QAの両方**を通す。
   数値 (忠実度) が上がっても、判定エンジンが通らない形になっていることがある。
